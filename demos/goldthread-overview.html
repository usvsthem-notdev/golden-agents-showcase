Governance layer for autonomous engineering work

goldthread

Most review checks the last diff. goldthread checks the thesis — the whole merged codebase against every rule, every time. On 24 Aug 2026, on a beer-rating app, that check caught a real safety gap that two separately passing reviews had already missed.

CASE STUDY — POURRATE  ·  6 thesis rules  ·  3 models routed  ·  $3.90 spent  ·  1 gap caught pre-release  ·  34 steps, 6 days, no reordering

Stage 00 — the failure mode

Passing every review, still shipping broken

Decompose a build into independent subtasks and each one gets reviewed on its own diff — and each one can legitimately pass. A rule like "report and block ships alongside posting" isn't violated by either piece alone, only by the two together, or apart. Per-diff review has no way to see that combination. Neither does a chat window that forgot the constraint three context resets ago.

goldthread doesn't trust the last diff. It re-reads the thesis into every call an agent makes, and it re-checks the whole merged codebase against it before anything ships — not because that's thorough, but because per-diff review provably isn't.

Stage 01 — the thesis

One sealed file, injected everywhere

GOLD_THESIS.md is written once, by a human, before any agent touches the project. It's sealed — file mode 444 — and re-injected into every model call any agent makes for the life of the project. Not a style guide a model happens to remember; a file nothing downstream gets to quietly forget.

That sounds simple until you actually try to make it hold. Two real incidents, found by attacking and auditing goldthread's own enforcement, not by reading its source and assuming it worked:

Guard hardening · 2026-08-20verified · 74/74

The first guard blocked writes by matching GOLD_THESIS.md as a literal, case-sensitive substring of the shell command. Six real bypasses got through before it was rewritten: rm -f deleted a sealed thesis outright — mode 444 stops redirects, not rm, because it protects the file's contents, not its directory entry — sed -i rewrote one in place, chmod 644 unsealed one, and three more slipped past as a glob, a case variant, and a quote-split filename.

Fixed by resolving real paths instead of matching strings. Verified live: an agent instructed to rm -f GOLD_THESIS.md in a covered profile made zero tool calls, and the thesis survived.

Coverage gap · 2026-08-22verified · 6/6 profiles

A harder bug, found by asking a different question: is the guard logic correct, or is it actually running where the work happens? It turned out to be mounted only in the PM profile — every profile that actually executes tasks had no guard at all, silently, since install.

"The guard is correct" and "the guard is running where it matters" are different claims, and only the second one protects anything. Installed and reverified across all six.

Stage 03 — case study: PourRate

A beer app, and the gap only a release-level check could catch

Chosen deliberately as a hard case: a social app for rating Guinness pours — a real alcohol-content product, real weight under iOS App Store guideline 1.4.3. Every number below is from one dated run, 2026-08-23 to 2026-08-24, not a simulation.

Seal — six rules, mechanically checkable

  • 01 Hard age gate before any pour content renders
  • 02 Rate the pour as a craft — never the drinking
  • 03 Report and block ship alongside posting, day one
  • 04 No gamification tied to volume or frequency
  • 05 Handle-only identity — no real name or phone number
  • 06 Permanent, non-dismissible responsible-drinking note wherever pour content renders

Plan — Fable, 27 seconds, one call

Given the build goal, the planner returned five subtasks — one per thesis rule, not a coincidence: the sealed thesis was injected into the planner's own context. Cost-aware routing correctly pulled the two compliance-critical pieces onto the strongest model:

#SubtaskDifficultyRouted to
1Hard age gate with persistent age-assurance statehighclaude-fable-5
2Pour rating model & composer, scoped to craft onlymediumclaude-sonnet-5
3Feed with permanent responsible-drinking noticemediumclaude-sonnet-5
4Report and block, server-side enforcementhighclaude-fable-5
5Handle-only identity, minimal-data signupmediumclaude-sonnet-5

The planner's own judgment matched what a careful human reviewer would flag: age gating and moderation enforcement are the two pieces most likely to fail subtly if done sloppily — and it routed exactly those back to itself.

Build — real defense in depth

The age gate shipped as three independent enforcement layers: routing (the content branch of the view hierarchy doesn't exist pre-pass), data (the feed store is a no-op unless passed), and network (the client re-checks and throws before a request is even constructed). It fails closed on corrupted storage; there is no "remind me later" state anywhere in the machine.

Rule 2 — rate the pour, not the drinking — is enforced at the API boundary, mechanically: the rating model rejects any field outside its four closed craft dimensions with an HTTP 422, not a comment asking nicely.

Disclosed honestly rather than smoothed over: the age-gate subtask shipped a Swift package; the composer subtask, with no shared-stack instruction, shipped React and Python. Nothing yet forces subtasks to converge on one stack — which is exactly what surfaces two sections down.

Review — per task, PASS

gt-review · t_1ac77a40pass · 6 / 6

Didn't take the worker's word for it — checked out the branch into a disposable worktree and independently re-ran the test suite (26/26) before citing exact file and line for every one of the six rule verdicts. Correctly passed Rule 3 for this diff alone, since it adds no posting surface — and explicitly flagged that the release-level check was still owed before this and the composer ship together.

$1.04 · real, priced

FAIL

The release-level check, not the per-task one, found it

A second review — scoped not to one diff but to the project's current default branch, everything merged, what would actually ship today — read the codebase whole. The iOS age gate is excellent. It covers exactly one of the app's two surfaces.

web/composer.html + backend/app/main.py — the only surface in the repo that can post or list content — has no age-assurance check anywhere. POST /ratings and GET /ratings are reachable by anyone, unauthenticated.

It ranked this above the also-real Rule 3 gap, with reasoning: an age gate on one surface and none on the other is not a partial pass, it's a bypass with a working front door. $0.88 · real, priced.

Fix — closing the loop that let it happen

The router's planner has no visibility into a project's existing code when it decomposes a new goal — which is exactly how the Swift/React split happened in the first place. Fixed for the avoidable half: before planning, the router now reads what the design studio's own scanners find already on disk, and tells the planner explicitly to extend it. Verified against a second, deliberately ambiguous goal on the same project: post-fix, the planner named the real gate files by class — AgeGatePolicy, AgeAssuranceStore, GateCoordinator — and required new work to route through them. Pre-fix, a grep for any of those names on the web surface returned zero matches.

A thesis is only a governance layer if nothing — not a worker, not a shortcut, not one unlucky diff — can ship around it. That's the bet goldthread makes. On 24 August 2026 it paid off exactly once, on a beer app, which is precisely the unglamorous place a real gap actually hides.
